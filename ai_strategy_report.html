1. 핵심 요약 (Executive Summary)

  • 현황: 모노레포를 LLM에 직접 주입 시 막대한 토큰 비용 및 환각(Hallucination) 발생.
  • 문제점: 기존 도구는 단순 파일 통합에 그쳐 고차원적 구조 정보 제공 불능.
  • 해결책: '의존성 없는 마이크로 서비스(MSA)' 체계로의 전환 필수.
  • 결론: 서비스 분할 및 API 규격화가 곧 최선의 프롬프트 엔지니어링임.

2. 배경: '바이브 코딩' 시대의 한계

최근 AI 에이전트를 활용한 개발(Vibe Coding)이 확산됨에 따라, 전체 코드베이스를 AI에게 이해시키기 위한 전처리 비용이 급증하고 있습니다.

  • 컨텍스트 과부하: 프로젝트가 비대할수록 불필요한 코드 분석으로 토큰 소모 증가.
  • 문서화의 역설: AI를 보조하기 위해 인간이 다시 고비용 문서 작업에 투입되는 모순 발생.

3. 기존 도구 분석 및 선분석 도구의 필요성

시중의 오픈소스(Repomix, Gitingest)는 대규모 모노레포 대응에 한계가 명확합니다.

  • 기존 도구: 단순 텍스트 팩킹 기반의 '수준 낮은 요약' 제공.
  • 선분석 도구 : AST(tree-sitter) 및 의존성 그래프(networkx)를 활용하여 LLM에 '추론 가이드' 제공.

4. 전략적 대안: MSA 기반 API 분할

가. 컨텍스트 물리적 격리

서비스를 독립 레포지토리로 분리하여 AI가 분석해야 할 절대량을 제한하고 수정 정확도를 극대화합니다.

나. 인터페이스 기반 협업

API 명세서(Swagger, gRPC)만으로 AI 간 협업이 가능하며, 이는 그 자체로 최적의 인스트럭션이 됩니다.

다. 문서·코드 동기화와 Swagger(OpenAPI)

초기에 별도 문서로 보고서·명세를 작성해 두고, 개발이 진행되면서 코드만 바꾸고 문서를 함께 갱신하지 않으면 문서와 구현이 어긋나는 현상이 누적됩니다. 그 상태에서는 코딩 에이전트가 컨텍스트로 오래된 문서를 다시 끌어다 쓰기 쉬워, 잘못된 전제로 수정 제안이 나올 위험이 커집니다.

이에 비해 Swagger(OpenAPI)처럼 엔드포인트·스키마·설명을 코드에 인접한 형태(주석, 데코레이터, 애너테이션 등)로 두면, 에이전트가 해당 파일을 수정할 때 같은 맥락에서 스펙도 함께 손대는 경향이 강합니다. 즉 API 범위에 한해서는 “구현과 문서가 한 덩어리”로 취급되기 쉬워, 별도 마크다운·외부 문서만 두는 방식보다 동기화 비용이 훨씬 낮고 에이전트 기반 개발에 유리합니다.
